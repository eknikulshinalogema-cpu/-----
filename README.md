# Дашборд аналитики сделок CRM для Битрикс24 (VibeCode)

Встраиваемое в левое меню Битрикс24 приложение, показывающее аналитику
по сделкам CRM: сводку по стадиям воронки, ключевые показатели и
последние сделки — с фильтрами по периоду, воронке и сотрудникам.

## Функции

- **Сводка по стадиям воронки** — таблица: ответственный (ФИО), воронка,
  количество сделок, стадия, сумма по стадии.
- **Ключевые показатели** — таблица: ответственный, воронка, сумма
  открытых сделок, количество выигранных сделок за период, средний чек;
  отдельной строкой — итог по всем строкам.
- **Последние сделки** — до 20 сделок: ответственный, воронка, название,
  сумма, текущая стадия.
- **Фильтр по периоду создания** — весь период (по умолчанию), сегодня,
  вчера, неделя, месяц, квартал, год, произвольный диапазон.
- **Фильтр по воронке** — конкретная воронка или «Все воронки».
- **Фильтр по сотрудникам** — мультивыбор; по умолчанию показаны все
  сотрудники, у которых есть сделки под текущим периодом/воронкой.
- Явные пустые состояния («Нет данных»), индикаторы загрузки,
  автообновление всех трёх блоков при смене любого фильтра.

## Архитектура (BFF)

```
Битрикс24 (левое меню, iframe)
        │  открывает приложение
        ▼
   Gateway VibeCode  ──── редиректит на appUrl, на каждый запрос
        │                 добавляет заголовок X-Vibe-Authorization
        ▼
  наш бэкенд (Express)  ──── пересылает Bearer-сессию как
        │                     Authorization: Bearer <...>
        ▼
   VibeCode Entity API (https://vibecode.bitrix24.tech/v1)
        │
        └─→ Битрикс24 CRM (сделки, воронки, стадии, сотрудники)
```

Фронтенд **не обращается к VibeCode API напрямую** — только к своему
бэкенду (`/api/dashboard/*`). Ключ приложения (`X-Api-Key`) и токен
сессии сотрудника (`Authorization: Bearer`) существуют только на
сервере и никогда не попадают во фронтенд, в логи или в ответы API.

### Модель авторизации — важный момент

Ключ приложения (`vibe_app_local_...`, тип «ключ авторизации» / OAuth-app)
сам по себе не даёт доступа к данным CRM. Для каждого запроса к сущностям
(сделки, статусы, воронки, пользователи) платформа **обязательно**
требует ещё и заголовок `Authorization: Bearer <токен сессии>` —
это токен конкретного сотрудника, который сейчас смотрит приложение.

Этот токен приложение не запрашивает само: когда сотрудник открывает
пункт меню в Битрикс24, Gateway VibeCode сам обменивает данные плейсмента
на сессию и на каждый последующий запрос кладёт её в заголовок
`X-Vibe-Authorization`. Наш бэкенд (`backend/middleware/auth.js`) читает
этот заголовок из входящего запроса и пересылает его дальше как
`Authorization: Bearer` при каждом вызове к VibeCode API
(`backend/services/vibeApi.js`).

Следствие: если открыть `appUrl` **напрямую в браузере, не через левое
меню Битрикс24**, заголовка `X-Vibe-Authorization` не будет, и
приложение покажет сообщение «Откройте приложение через левое меню
Битрикс24» — это ожидаемое поведение, а не ошибка.

Поскольку данные читаются с правами того сотрудника, который открыл
приложение (а не с правами одного общего сервисного ключа), дашборд
показывает ровно те сделки, которые видны этому сотруднику в самом
Битрикс24 — разграничение доступа отдаёт сама CRM.

## Используемые скоупы и обоснование

- **`crm`** — чтение сделок (`/v1/deals`), справочника воронок
  (`/v1/deal-categories`) и справочника стадий (`/v1/statuses`). Это
  основные данные, на которых строится вся аналитика.
- **`user`** — чтение списка сотрудников (`/v1/users`) для отображения
  ФИО ответственного в таблицах и построения списка в фильтре по
  сотрудникам.

Ключ работает в режиме **READONLY** — приложение только читает данные,
никаких операций записи/изменения сделок не выполняет.

## Структура проекта

```
backend/
  config.js               — загрузка конфигурации из .env
  server.js                — точка входа Express, отдаёт статику фронтенда
  routes/dashboard.js      — эндпоинты /api/dashboard/*
  services/vibeApi.js      — HTTP-клиент VibeCode Entity API:
                              пересылка Bearer, retry/backoff на 429,
                              разбор реальных кодов ошибок платформы
  services/crm.js          — бизнес-логика: воронки, стадии, сотрудники,
                              сделки, построение трёх отчётов
  middleware/auth.js        — чтение заголовков Gateway
                              (X-Vibe-Authorization и др.)
  utils/validation.js       — валидация входных параметров запросов
  utils/dateRange.js        — вычисление диапазона дат по period
  utils/cache.js            — кэш справочников (TTL 5 минут)
  utils/logger.js           — логирование без чувствительных данных
  .env.example              — шаблон переменных окружения (без секретов)
frontend/
  index.html                — разметка дашборда, включая фильтр по сотрудникам
  css/style.css             — стили в цветовой схеме Битрикс24
  js/app.js                 — логика фильтров и рендеринга таблиц
```

## Эндпоинты бэкенда

| Метод | Путь | Параметры | Описание |
|---|---|---|---|
| GET | `/api/dashboard/funnels` | — | список воронок для фильтра |
| GET | `/api/dashboard/employees` | `period, from, to, funnel` | список сотрудников с хотя бы одной сделкой под фильтром |
| GET | `/api/dashboard/stages` | `period, from, to, funnel, employees` | сводка: сотрудник × воронка × стадия |
| GET | `/api/dashboard/metrics` | `period, from, to, funnel, employees` | ключевые показатели: сотрудник × воронка + итоговая строка |
| GET | `/api/dashboard/recent` | `period, from, to, funnel, employees, limit` | последние сделки (по умолчанию до 20) |
| GET | `/api/health` | — | проверка живости сервиса |

Параметр `period`: `all` (по умолчанию) \| `today` \| `yesterday` \|
`week` \| `month` \| `quarter` \| `year` \| `custom` (требует `from`/`to`
в формате `YYYY-MM-DD`). Параметр `funnel`: ID воронки или `all`.
Параметр `employees`: список ID через запятую, либо отсутствует/`all`
для всех сотрудников.

Внутри каждого запроса к бэкенду поднимается вся выборка сделок под
фильтр (через `POST /v1/deals/search` с курсорной пагинацией по `id`,
до 5000 записей) и агрегируется на сервере — это и даёт группировку по
сотруднику/воронке/стадии сразу в трёх нужных разрезах.

## Обработка ошибок

Бэкенд разбирает реальные коды ошибок платформы VibeCode
(`error.code` в теле ответа) и превращает их в понятные сообщения:

| Ситуация | Сообщение пользователю |
|---|---|
| Нет `X-Vibe-Authorization` / истёкшая сессия | «Откройте приложение через левое меню Битрикс24 — сессия отсутствует или истекла» |
| `KEY_EXPIRED` / `KEY_INACTIVE` | «Ключ доступа приложения недействителен, обратитесь к администратору» |
| `BITRIX_ACCESS_DENIED` / 403 | «Недостаточно прав для просмотра данных» |
| 429 / `RATE_LIMITED` | «Слишком много запросов, подождите...» (автоматический retry с учётом заголовка `Retry-After`) |
| 502 / `BITRIX_UNAVAILABLE` | «Сервис временно недоступен» |
| прочие | общее сообщение пользователю, подробности — в серверном логе |

## Известные ограничения

- Аналитика охватывает только сущность «Сделки» (Deals); лиды и другие
  сущности CRM не включены.
- Лимит выборки — 5000 сделок на один запрос с текущим набором
  фильтров; на очень широком периоде без уточнения воронки/сотрудника
  возможна неполная выборка — в этом случае стоит сузить период.
- Множественный выбор сотрудников использует оператор фильтра `$in`
  API VibeCode.
- Название стадии сопоставляется по полному коду стадии (например,
  `C97:WON` для пользовательской воронки, просто `WON` — для
  дефолтной) — так поддерживаются любые пользовательские воронки
  Битрикс24, а не только стандартная.

## Как проверить

1. Открыть приложение через левое меню Битрикс24 (плейсмент уже
   привязан) — либо для локальной отладки:
   ```bash
   cd backend
   npm install
   npm start
   ```
   и открыть `http://localhost:3000/` (без реальной сессии Битрикс24
   данные не загрузятся — сработает ожидаемое сообщение о необходимости
   открытия через меню, см. раздел про авторизацию выше).
2. `GET /api/health` должен вернуть `{"status":"ok"}`.
3. Проверить смену фильтров (период / воронка / сотрудники) — все три
   блока данных должны обновляться автоматически без перезагрузки
   страницы.
4. Проверить пустые состояния: при выборе сочетания фильтров без
   данных везде должно быть «Нет данных», а не ошибка.
5. Убедиться, что нигде — ни в статике фронтенда, ни в ответах API —
   не встречается значение ключа `VIBE_API_KEY`.

## Переменные окружения (`.env`)

```
VIBE_API_KEY=<ключ авторизации приложения (vibe_app_...)>
PORT=3000
NODE_ENV=production
```

`.env` добавлен в `.gitignore` и не должен попадать в систему контроля
версий — ключ передаётся на сервер деплоя отдельно, через параметр
`env` тела запроса `POST /v1/infra/servers/:id/deploy`.
